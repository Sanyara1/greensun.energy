# Отдельная первая установка /news/

Статус на 25.10.2026: подготовлено для проверки, НЕ РАЗРЕШЕНО К ПУБЛИКАЦИИ.
Это операторский порядок, не выполненная установка. SSH-доступа к VPS в этой сессии нет; действующая конфигурация nginx ещё не прочитана. Обязательную проверку конфигурации нельзя заменить ответом HTTP или прежним install.py.

## Границы

Устанавливаем только новый каталог `news/`. Не копировать корневой `index.html` из GitHub, весь репозиторий, `review.json`, тесты или служебные документы в web root. Не выполнять общий deploy/rsync с `--delete`. Не менять systemd, ботов, очередь Telegram V6, lead API, конфигурацию nginx или основной sitemap этим изменением. Если `/news/` уже появился — остановиться: этот порядок предназначен только для первой установки.

В историческом пакете сайта указаны `/var/www/greensun.energy`, `/etc/nginx/sites-available/greensun.energy` и общий lock `/var/backups/greensun.energy/.deploy.lock`. Это подсказки для проверки, не подтверждение актуальной конфигурации.

## 1. Проверка на VPS (до любых изменений рабочего дерева)

Запустить от оператора с правом чтения nginx после сверки docroot:

```sh
sudo python3 preflight_site.py \
  --site-root /var/www/greensun.energy \
  --output /var/backups/greensun-news-audit-YYYYMMDD-HHMMSS
```

Заменить суффикс на текущий момент, каждый раз использовать новый каталог. Скрипт выполняет `nginx -T`, строит хеши актуального дерева, сверяет выдачу `/` через HTTPS локального origin с `index.html`, сохраняет robots и sitemap. Он ничего не устанавливает и не создаёт резервную копию всего сайта. Снимок конфигурации приватный; не коммитить его в публичный GitHub.

Оператор должен прочитать `nginx-T.txt`: правильные `server_name`, TLS-vhost и `root`; обработка `index.html`; нет перехвата `/news` прокси, SPA fallback, auth, `deny`, regex-location или `X-Robots-Tag: noindex`; MIME для HTML/CSS/SVG/PNG/XML. Проверить redirect HTTP→HTTPS, www→основной домен, `/news`→`/news/`; неизвестный адрес должен давать 404. Проверить существующую robots-политику для `/news/`. Если нужны изменения nginx — отдельный diff, проверка и согласование до продолжения. Не вставлять типовой server-блок поверх рабочего.

## 2. Решение владельца и окончательная сборка

Владелец отдельно подтверждает точные текст, иллюстрацию, раскрытие направления и публикацию на `https://greensun.energy/news/digital-engineer/`. Предыдущие одобрения ноябрьских постов не применяются. Заполнить копию `approval.example.json` только по фактическому решению; `candidate_sha256` взять из проверенного preview/review.json. `decision_ref` — ссылка/идентификатор этого решения, `approved_at` — его время, `published_at` — фактическая дата выпуска с часовым поясом, например `+03:00`. Не использовать 24 октября просто потому, что это дата черновика.

```sh
python3 build_news_preview.py --mode public \
  --approval /private/path/owner-approval.json \
  --output /private/path/gsun-news-release-YYYYMMDD-HHMMSS
```

JSON-квитанция — запись оператором решения, а не электронная подпись и не независимая аутентификация владельца. Сам факт технического прохождения gate не создаёт согласование. Записи `test://` и синтетические решения тестов не использовать для установки. Сборка не публикует; `published_at` журнала остаётся null до проверки HTTP. Метаданные HTML и `<time>` получают время выпуска из квитанции. При смене даты или версии пересобрать и повторить проверки. Служебная квитанция всегда вне `news/`.

## 3. Резервирование и подготовка отката

Непосредственно перед установкой, под существующим общим `.deploy.lock`:

1. Повторить preflight; сравнить конфигурацию и всё дерево с просмотренным снимком. При любых расхождениях — STOP и разбор. Не считать вчерашний snapshot актуальным.
2. Создать уникальный приватный каталог в `/var/backups/greensun.energy/` с правами 0700. Архивировать актуальное дерево сайта (`tar -C /var/www -cpf "$backup/site.tar" greensun.energy`) и `/etc/nginx` (`tar -C /etc -cpf "$backup/nginx.tar" nginx`), сохраняя атрибуты. Эти команды допустимы только после подтверждения путей. Не копировать базы заявок, SMTP-файлы или секреты приложения.
3. Сохранить `preflight.json`, исходную квитанцию, `review.json`, время и хеши архивов. Проверить архивы чтением `tar -tf`; распаковать копию site.tar в приватный временный каталог и сравнить инвентарь через `tree()` из preflight_site.py. Так проверяется восстанавливаемость, не только существование архива.
4. Скопировать только release/news в новый закрытый staging-каталог **рядом с docroot, за пределами обслуживаемого дерева**, на той же файловой системе. Проверить полный список и SHA-256 по `review.json`; отказаться от симлинков и специальных файлов. Публичные файлы: 0644, каталоги: 0755, доступные пользователю nginx. Убедиться, что nginx не обслуживает staging через другой vhost/alias.
5. Подготовить до переключения guarded rollback: проверить, что установленный news имеет тот же inode и полный набор хешей, что staging; только при совпадении переименовать его обратно в уникальный приватный каталог вне web root. При позднейших изменениях news не затирать их — STOP. Основное дерево не восстанавливать целиком, поскольку это затёрло бы чужие обновления.

## 4. Установка и приёмка

Только после решения владельца и успешных шагов выше:

- Повторно проверить отсутствие `$site/news`, совпадение snapshot и наличие блокировки.
- Атомарно перенести подготовленный staging в `$site/news` на той же FS с запретом замены существующего назначения (Linux `renameat2(RENAME_NOREPLACE)`). Не использовать обычный `mv`, который может вложить каталог в уже появившийся news. Перезагрузка nginx при обычной статической выдаче не требуется.
- Сначала на локальном origin через `curl --resolve greensun.energy:443:127.0.0.1`, затем через внешний HTTPS проверить `/news/`, `/news/digital-engineer/`, все assets и `/news/sitemap.xml`: 200, правильные MIME, байты/хеши как в release. Проверить отсутствие noindex в HTML **и** заголовках.
- Проверить canonical и og:url; OG PNG — 1200×630 и доступен без авторизации. Дата в статье, OG и sitemap одинакова. `/news` и `/news/digital-engineer` корректно ведут на адреса с `/`; `/news/review.json` и случайный несуществующий адрес — 404.
- Проверить переход список→статья→список, главную и ссылку на форму контактов. Повторить wide/mobile визуальный просмотр уже с реального домена.
- Сверить хеши всех файлов вне news и конфигурации с preflight: они должны совпасть. GET-проверка существующей формы без отправки заявки. Очередь Telegram не читать и не менять установщиком.

При провале любой проверки — выполнить подготовленный откат **только news**; проверить возвращение прежнего HTTP-статуса и неизменность главной. Сохранить причину и журнал, не отмечать публикацию успешной.

Лишь после всех проверок создать приватную квитанцию `PUBLISHED_VERIFIED` с URL, фактическим временем установки, candidate_sha256, commit, manifest/hash, результатами HTTP и путём резервной копии. Сам файл сборки не свидетельствует о публикации.

## 5. Sitemap и обнаружение

Публичная сборка создаёт обычную отдельную sitemap: `https://greensun.energy/news/sitemap.xml`, только два канонических URL. До публикации sitemap отсутствует. Её можно отдельно отправить через кабинет вебмастера после приёмки.

Текущий корневой `/sitemap.xml` — urlset из 19 URL, а не sitemapindex (внешнее чтение 25.10.2026). Для единого sitemap позже добавить два URL к **свежему** файлу, сохранив все существующие записи, с отдельной резервной копией и diff. Не вкладывать sitemap в urlset и не заменять корневую карту файлом из этой сборки. Альтернатива — согласованно добавить вторую строку Sitemap в текущий robots.txt. Ни один из этих корневых файлов сейчас не меняется.

Ссылку «Новости» в актуальной главной подготовить отдельным изменением после получения рабочего файла. Текущий PR намеренно не подменяет главную и не обеспечивает вход в новости из её меню. Доступ по прямому URL и sitemap не гарантирует индексацию.
